## Why

요구 30번의 핵심은 "개발자의 추가 작업 없이 CASE 생성 → 질문 입력 → 정답 설정 → QR 생성 →
출력 → 책에 설치 → 운영 → 통계"다. 지금 관리자 화면은 그룹 생성과 퀘스트 1건 생성/수정만
가능하고, 단계 순서·정답 유형·미리보기·상태·복제가 없다. 이 티켓이 CMS를 완성한다.

## Mini-tickets

1. **13-1 대시보드** — 진행 중/전체 CASE, 오늘 참가·완료, [새 CASE 만들기].
   오늘 참가·완료는 [16](16-completion-code-and-stats.md) 전까지 `-`로 표시해도 된다(16에서 연결됨).
2. **13-2 CASE 목록·생성·복제·상태** — 카드에 상태 배지(DRAFT/TEST/LIVE/CLOSED),
   단계 수, [편집] [미리보기] [통계] [복제] [삭제]. 복제는 단계·설정을 모두 복사하되
   **단계 id와 `qrToken`은 새로 발급**하고 상태는 DRAFT로 시작한다.
3. **13-3 STEP 목록과 순서 변경** — 단계 목록(이름·종류·공개 여부·QR 유무),
   드래그로 순서 변경(`StepRepo.reorder`), [단계 추가].
4. **13-4 STEP 편집기 - 기본/콘텐츠** — 이름·번호·공개·제목·본문·미디어 업로드(→ 15).
5. **13-5 STEP 편집기 - 질문/정답** — `AnswerSpec` 유형 선택 시 편집 폼이 바뀐다.
   - 객관식/복수 선택: A~D 보기 입력 + 정답 체크
   - 단답형: 정답 여러 개(줄 단위 입력) + 포함/일치 선택
   - 숫자: 정답 + 허용 오차
   - 키워드: 키워드 목록 + 모두/하나라도
   - 정답이 비어 있으면 저장을 막고 이유를 표시한다.
6. **13-6 피드백·힌트·다음 단계** — 힌트, 정답/오답 메시지(비우면 기본 문구), 다음 단계 표시.
7. **13-7 미리보기** — 편집 폼 오른쪽에 참가자 화면을 그대로 그리는 패널. **저장하지 않은
   초안 상태로** 렌더한다(재작업 전에는 서버 미리보기 API + iframe이었다).
8. **13-8 테스트 모드** — 관리자가 실제 참가자처럼 처음부터 끝까지 진행.
   모든 단계 접근, [정답 보기] 토글, [단계 초기화], [완료 상태 초기화].
   세션에 `isTest = true`를 표시해 통계에서 제외한다([16](16-completion-code-and-stats.md)).
9. **13-9 LIVE 전환 검증** — LIVE로 바꾸기 전에 검사하고 위반 목록을 보여주며 거부한다.
   - 모든 QR/FINAL 단계에 `answerSpec`이 있는가
   - 순서에 구멍이 없는가, QR 단계에 `qrToken`이 있는가
   - 시작(`entryToken`)·FINAL 이후 완료 화면이 존재하는가
   - INTRO 본문이 비어 있지 않은가

### 미리보기는 저장을 거치지 않는다 (2026-09-15 재작업)

처음에는 단계 카드의 [미리보기] 버튼이 iframe 다이얼로그를 열고, 그 안의 `/admin/preview/$stepId`
라우트가 **서버의 미리보기 API**(`getStepForPreview`)로 초안을 받아 그렸다. 이 방식의 문제는
두 가지였다.

- **한 번 저장해야 보인다.** 미리보기가 서버에서 오므로 "고치고 → 저장하고 → 다시 열어보는"
  왕복이 필요하다. 정작 확인하고 싶은 순간(타이핑하는 중)에는 아무것도 반영되지 않는다.
- **"정답을 맞히면 나오는 단서"를 볼 수 없다.** 정답 화면은 실제로 맞혀야 나오므로, 관리자는
  자기 눈으로 연출·문구를 확인할 방법이 없었다.

지금은 `StepPreviewPanel`이 편집 폼 **안에서** `useFormContext().watch()`로 값을 읽어 그린다.

- 폼(왼쪽) · 미리보기(오른쪽) 2단. 다이얼로그 폭은 `dialog` 레시피의 `size: wide`(5xl).
  좁은 화면에서는 미리보기가 폼 아래로 내려간다(`lg` 미만).
  - `size`는 `DialogShell`이 prop으로 받아 런타임에 넘기므로 Panda가 그 variant를 알 수 없다.
    `staticCss: [{ size: ["*"] }]`를 달지 않으면 클래스만 붙고 폭은 그대로다 — 실제로 이
    상태로 만들었다가 테스트가 잡았다(계산된 `max-width`를 보는 테스트). `revealAnimation`과
    같은 함정이다(→ [15](15-media-and-reveal.md)).
  - 기본값은 `md`(28rem)라 다른 다이얼로그(확인 창)는 예전 폭 그대로다.
- 미리보기는 위가 **문제**, 아래가 **정답을 맞히면 보이는 단서**다. 단서는 `RevealPanel`을
  그대로 써서 연출·사운드까지 실제와 같고, [다시 보기]로 연출을 되돌려 본다(프리셋을 바꾸면
  자동으로 다시 돈다 — 연출은 마운트 때 한 번만 재생되므로 `key`로 다시 앉힌다).
- **참가자 컴포넌트(`StepCardForm`)를 재사용하지 않는다.** 중첩 `<form>`이 생기고, 눌러도
  아무 일이 없는 제출 버튼이 "동작하는 화면"처럼 보인다. 대신 같은 모양을 옮겨 그리되 입력
  요소는 전부 `disabled`로 두고, "여기서 눌러도 저장되지 않아요"를 적어 둔다.
- 미리보기는 저장 가능 여부를 판단하지 않는다. 정답을 아직 안 골랐어도 적어 넣은 보기를
  그대로 보여준다(`toAnswerSpec`은 저장 검증용이라 여기서는 쓰지 않는다).
- 단서 문구가 비면 정답 메시지가, 그것도 비면 기본 문구가 그 자리를 채운다 — 참가자
  화면(`step-experience.tsx`)과 같은 규칙이다.
- **PC/모바일 프레임은 없앴다.** 참가자는 QR을 찍고 자기 휴대폰으로 들어온다. 두 프레임을
  나눠 보는 비용에 비해 확인할 게 없었고, 미리보기 자체가 좁은 칸이라 참가자가 보는 폭에
  가깝다.
- 서버의 미리보기 API(`GET /api/steps/:id/preview`)와 그 테스트는 그대로 남겨 뒀다.
  UI가 쓰지 않게 됐으니, 이 API를 계속 둘지는 별도로 판단한다.

## 화면 원칙

- 미리보기는 편집기 안에 항상 함께 있다. "고치는 즉시 확인 → 만족하면 저장"이 기본 흐름.
- 파괴적 동작(삭제, 순서 초기화)은 확인 다이얼로그 + outline 버튼.
- 관리자 화면의 용어는 요구서의 단어(CASE, STEP, 단계, 단서, 정답 유형)를 그대로 쓴다.
  코드 타입과 화면 단어를 일치시켜 CMS 유지보수 비용을 낮춘다.

## Explicitly deferred

- CASE 단계 복사, 콘텐츠 되돌리기(버전 관리), 예약 공개/종료일.
- 관리자 계정 다중화와 역할(SUPER ADMIN / CONTENT ADMIN / VIEWER) — 계획 §11 보류 항목.
- 이미지 기반 미션 등 신규 정답 유형.

## Acceptance criteria

- 개발자 개입 없이 CASE를 복제해 새 CASE를 만들고, 단계 순서·질문·정답 유형·힌트를 수정할 수 있다.
- 저장 전에 참가자 화면과 정답을 맞혔을 때의 단서를 편집기 안에서 확인할 수 있다.
- 정답이 빠진 단계가 있으면 LIVE로 전환되지 않고 이유가 보인다.
- 테스트 모드로 전체 동선을 돌려보고 진행을 초기화할 수 있다.
