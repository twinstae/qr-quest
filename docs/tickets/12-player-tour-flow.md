# 12. 참가자 투어 플로우 (시작 → 사건 종결)

Status: Not started. Phase 1의 핵심. 이 티켓이 끝나면 실제로 체험비를 받고 운영할 수 있다.
PLAN.md item: 12
상위 설계: [../plans/qr-mystery-tour.md](../plans/qr-mystery-tour.md) §4~§5

## Why

지금 참가자 화면은 "QR 1개 = 문제 1개"로 끝난다. 요구서의 실제 경험은
START → 사건 소개 → QR 01~04 → FINAL → CASE CLOSED의 **순차 진행**이고,
참가자가 다음 QR을 실제로 찾지 못하면 넘어갈 수 없어야 한다(요구 11).
또한 참가자가 URL을 직접 입력해 단계를 건너뛰는 경우까지 고려해야 한다(요구 11 후단).

현재는 세션이 없으므로 진행·재개·통계가 모두 불가능하다. 이 티켓이 그 토대를 만든다.

## Scope

### 세션

- 시작 QR(`/s/{entryToken}`) 진입 시 서버가 세션을 생성한다.
  - `token`은 추측 불가 32자. **httpOnly 쿠키**로 내려보내고, 화면 갱신·기기 변경 대비
    화면에 "이어하기 링크"도 남긴다(개인정보는 수집하지 않는다).
  - 같은 시작 QR을 다시 스캔하면 **진행 중 세션을 이어간다. 새 세션을 만들지 않는다.**
    이미 완료한 세션이면 완료 화면(인증번호 포함)을 다시 보여준다.
- 개인정보는 수집하지 않는다(요구 12). 저장 항목은 계획 §4의 `PlaySession` 그대로.

### 잠금 (서버 강제)

- 모든 참가자 조회/제출은 서버에서 `openStep`을 통과해야 한다.
  - `LOCKED` → 423과 함께 `{ currentStepOrder, requestedOrder, stepName }`을 내려준다.
  - `NOT_STARTED` → "먼저 시작 QR을 찍어주세요" 안내 상태를 내려준다.
  - `OTHER_CASE` → "이 QR은 다른 사건의 것이에요" 안내 상태.
- 클라이언트는 잠금을 판단하지 않는다(표시만 한다). **URL을 직접 입력해도 우회 불가.**
- 단계 조회 응답에 `answerSpec`/정답은 절대 포함하지 않는다(회귀 테스트로 고정).

### 화면

| 화면              | 라우트                     | 특징                                                                   |
| ----------------- | -------------------------- | ---------------------------------------------------------------------- |
| 시작 표지         | `/s/$entryToken`           | CASE 번호·제목·한 줄 소개·예상 시간·[사건 시작]                        |
| 사건 소개 (INTRO) | `/play/$caseId` step=INTRO | 배경 서사 + [사건 시작]                                                |
| 단서 찾기         | `/play/$caseId` (대기)     | "N번째 단서를 찾아주세요"                                              |
| 문제 (QR/FINAL)   | `/t/$qrToken` → 문제 화면  | 유형별 입력 UI + [힌트] + [정답 제출]                                  |
| 단서 공개         | 정답 후 전환               | `reveal` 표시 + [다음 단서 찾기] (연출은 [15](15-media-and-reveal.md)) |
| 순서 아님         | 잠금 시                    | 현재 위치 안내 + [지금 단계로 돌아가기]                                |
| CASE CLOSED       | FINAL 정답 후              | 사건 해결 + **완료 인증번호** + 소요 시간·힌트 횟수                    |
| 재개·오류         | 공통                       | 네트워크 재시도(입력값 보존), 다른 기기에서 이어하기                   |

- 입력 UI는 `AnswerSpec`의 분기별로 컴포넌트를 나눈다:
  `ChoiceFields`(SINGLE/MULTI), `TextAnswerField`(SHORT_TEXT/NUMBER), `KeywordAnswerField`.
  기존 `QuestCardForm`은 이 조합으로 대체한다.
- 오답은 실패 처리가 아니다(요구 8): 횟수 제한 없음, 재시도 버튼, 입력값 유지.
- 힌트는 **별도 엔드포인트**로 분리한다: `POST /api/play/steps/:id/hint`.
  힌트를 조회 시점에 함께 내려주면 "사용했는지"를 알 수 없어 통계가 불가능해진다.
- Wake Lock으로 진행 중 화면 꺼짐을 막는다(미지원 브라우저는 조용히 무시).
- `/quest/$questId`를 제거하고 `quest-qr-code.tsx`를 `entryToken`/`qrToken` 기반으로 교체한다.

### 완료 인증번호

- FINAL 정답 시 `79-1-XXXX` 형식 코드를 발급해 세션에 저장한다(요구 14).
- 혼동되는 문자(O/0, I/1)를 제외한 알파벳·숫자 4자리를 쓴다.
- 발급·재표시·리딤 처리는 [16](16-completion-and-stats.md)에서 확장하고,
  이 티켓에서는 발급과 화면 표시까지 한다.

## 테스트 (RED 먼저)

- `src/application/playService.test.ts`
  - 시작 QR → 세션 생성, currentStepOrder = INTRO 순서
  - 같은 시작 QR 재스캔 → 새 세션을 만들지 않고 기존 세션 반환
  - 순서 건너뛴 단계 조회 → `LOCKED`
  - 세션 없이 단계 진입 → `NOT_STARTED`
  - 다른 CASE의 단계 → `OTHER_CASE`
  - 정답 제출 → currentStepOrder 전진 + `StepAttempt` 기록
  - 오답 → 전진하지 않음, 시도 기록은 남음, 횟수 제한 없음
  - 힌트 요청 → `usedHint` 기록, 같은 단계에서 반복 요청해도 1회로 집계
  - FINAL 정답 → COMPLETED + 완료 코드 발급
  - 완료 후 재진입 → 완료 화면 데이터 반환
- `src/api/elysia/playRoutes.test.ts`
  - `GET /api/play/steps/:qrToken` 응답에 정답 정보가 없다
  - 순서 위반 → 423 + 현재 단계 안내
  - 타 CASE 토큰 → 안내 상태(4xx), 서버 에러 아님
- 브라우저 테스트(siheom)
  - 유형별 입력 UI 렌더와 제출
  - 오답 후 재시도 시 입력값 유지 + 안내 문구 노출(빨간 경고색 아님)
  - 진행 점이 현재 위치를 표시한다
  - 잠금 화면 문구와 복귀 버튼 동작
  - 초기 로드 시 단계 내용이 즉시 보인다(연출이 정보를 가리지 않음)

## Explicitly deferred

- QR 없이 이어보기용 매직링크 공유(2인 각자 폰으로 진행) — 요구는 "2인 1대"가 기본.
- 참가자 이름/연락처 입력, 예약 결제 연동.
- 오프라인(Cache Storage) 동작 — 매장 내 Wi-Fi 전제로 시작하고 필요 시 재검토.

## Acceptance criteria

- 시작 QR 1개와 단계 QR 4개, FINAL QR 1개로 전체 동선이 처음부터 끝까지 이어진다.
- 단계 QR을 순서와 다르게 찍으면 진행되지 않고 현재 위치를 안내한다.
- 단계 URL을 직접 입력해도 순서를 건너뛸 수 없다.
- 브라우저를 닫았다가 같은 시작 QR을 다시 찍으면 진행 상황이 유지된다.
- 참가자에게 전달되는 어떤 응답에도 정답이 포함되지 않는다.
- 오답 횟수 제한이 없고, 오답 화면이 좌절을 유발하지 않는다.
