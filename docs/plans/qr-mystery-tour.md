# 책방79-1 QR 미스터리 투어 — 개발 계획

Status: Plan (구현 전). 이 문서는 `PLAN.md` 항목 10~16의 상위 설계 문서다.
개별 작업 단위와 수용 기준은 `docs/tickets/10..16-*.md`에 있다.

## 0. 한 줄 정의

> 게임을 만드는 게 아니라, **책방지기가 개발자 도움 없이 직접 만들고 운영하는 콘텐츠 기반 QR 미스터리 투어 시스템**.

이 문장이 모든 우선순위 결정의 기준이다. 기능이 화려한가보다
"영업 중인 서점에서 사장님이 혼자 케이스를 하나 더 만들 수 있는가"가 중요하다.

## 2. As-Is: 지금 코드가 가진 것

**스택** — TanStack Start(Router/Start) + React 19, Elysia(TypeBox) `/api/*` 단일 마운트,
Drizzle + PGLite(개발/테스트)·Postgres(운영), better-auth, Panda CSS(+레시피/토큰),
valibot(폼) + Eden Treaty(타입 클라이언트), vitest(browser=Playwright / server=node),
`@siheom/react`, Storybook.

**구조** — `domain`(순수) / `application`(서비스) / `persistence`(repo 인터페이스 + Fake + Drizzle) /
`api`(Elysia) / `routes`(화면) / `components/domains`(도메인 컴포넌트). 이 구조는 유지한다.

**이미 있는 것**

| 영역                                                    | 상태                                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Quest = QR 1개 + 문제 1개 + 정답 1개 + 보상(text/image) | 단일 퀘스트 열람/정답 판정/보상 표시 동작                                         |
| QuestGroup                                              | 생성·목록만 (수정/삭제/조회 단건 없음)                                            |
| `/quest/$questId`                                       | QR 고정 URL → 서버에서 콘텐츠 조회 (**요구 23번은 구조적으로 이미 충족**)         |
| QR                                                      | SVG/Canvas 생성, PNG 다운로드, URL 복사 (`quest-qr-code.tsx`)                     |
| 관리자                                                  | 로그인, 그룹 목록/생성, 그룹별 퀘스트 목록, 퀘스트 생성/수정 다이얼로그           |
| 이미지                                                  | presign 업로드(S3/Supabase 어댑터 + Fake), 업로드 필드                            |
| 정답 판정                                               | `isCorrectAnswer` — trim+lowercase 단일 비교. `alternatives` 컬럼은 있으나 미사용 |

**없는 것 (요구서가 요구하는데 코드에 존재하지 않는 것)**

CASE/STEP 순서 개념, 단계 잠금, 참가자 세션, 진행률, 사건 소개·완료 화면,
정답 유형(객관식/숫자/키워드/복수선택), 힌트 사용 기록, 완료 인증번호,
CASE 복제·상태(DRAFT/TEST/LIVE/CLOSED), 미리보기, 테스트 모드, 통계, QR 출력 시트,
동영상/오디오, 공개 연출, 업로드 용량 안내.

## 3. 용어 정리: Quest → Case/Step

요구서의 CASE·STEP을 기존 `QuestGroup`·`Quest`에 대응시킨다. 이름을 바꾸는 이유는
관리자 화면의 문구와 코드 타입이 어긋나면 CMS 유지보수가 비싸지기 때문이다.
**아직 배포 전(티켓 09 미완료), 실사용 데이터가 없으므로 테이블 rename 마이그레이션을
지금 하는 것이 가장 싸다.**

| 요구서                    | 도메인 타입   | DB                          |
| ------------------------- | ------------- | --------------------------- |
| CASE                      | `Case`        | `cases` (구 `quest_groups`) |
| STEP (START/QR/FINAL/END) | `Step`        | `steps` (구 `quests`)       |
| 참가 세션                 | `PlaySession` | `play_sessions`             |
| 제출 기록                 | `StepAttempt` | `step_attempts`             |

`Step`은 `order`(정렬) + `kind`(INTRO / QR / FINAL / CLOSING)로 구분한다.
요구서 18번이 START·END도 편집 목록에 넣으라고 했으므로, **모든 화면을 Step으로 통일**하고
CASE 생성 시 기본 단계 7개(INTRO → QR×4 → FINAL → CLOSING)를 자동 생성한다.
관리자는 빈 화면을 마주하지 않고, 편집기는 한 종류만 만들면 된다.

## 4. 도메인 모델 (초안)

```ts
export type Case = {
  id: string;
  number: number; // CASE 01
  title: string; // 사라진 책의 행방
  teaser: string; // 한 줄 소개 (시작 화면)
  intro: string; // 사건 배경 본문 (INTRO 화면 기본값)
  thumbnail?: Media;
  estimatedMinutes: number; // 15~20
  status: "DRAFT" | "TEST" | "LIVE" | "CLOSED";
  entryToken: string; // 시작 QR = /s/{entryToken}
  finalBookTitle?: string; // 최종 정답 책
  rewardNote?: string; // 완료 기념품 안내
};

export type Step = {
  id: string;
  caseId: string;
  order: number;
  kind: "INTRO" | "QR" | "FINAL" | "CLOSING";
  name: string; // "QR 02"
  qrToken: string | null; // QR 단계만. URL = /t/{qrToken}
  published: boolean;
  title: string; // 단서/문제 제목
  body: string; // 본문
  media?: Media; // 이미지 또는 동영상
  reveal: {
    // 정답 시 공개되는 것 (기존 reward)
    text?: string;
    media?: Media;
    preset?: RevealPreset; // 연출
    sound?: SoundKey;
  };
  question?: string;
  answerSpec?: AnswerSpec;
  placeholder?: string;
  hint?: string;
  correctMessage?: string; // 기본 "정답입니다"
  wrongMessage?: string; // 기본 "아직 사건의 핵심에 도달하지 못했어요"
};
```

**정답 유형은 판별 유니온 하나로 모은다** (요구 20번). 판정 로직은 순수 함수 하나이므로
테스트가 가장 싸고, 관리자 UI는 이 유니온의 각 분기마다 편집 폼 하나씩만 만들면 된다.

```ts
export type AnswerSpec =
  | { type: "SINGLE_CHOICE"; choices: Choice[]; correctChoiceIds: string[] } // A/B/C/D
  | { type: "MULTI_CHOICE"; choices: Choice[]; correctChoiceIds: string[] } // 순서 무관
  | { type: "SHORT_TEXT"; accepted: string[]; match: "EXACT" | "CONTAINS" }
  | { type: "NUMBER"; accepted: number[]; tolerance?: number }
  | { type: "KEYWORDS"; keywords: string[]; match: "ALL" | "ANY" };
```

정규화 규칙(순수 함수, 테스트 대상): NFC 정규화 → 앞뒤 공백 제거 → 연속 공백 1칸 →
소문자화 → SHORT_TEXT일 때 문장부호 제거. 퍼지 매칭(초성·유사어)은 **하지 않는다**.
대신 "정답을 여러 개 등록할 수 있다"로 해결한다 — 관리자가 통제 가능하고, 오탐이 없다.

**세션과 잠금**은 서버가 판단한다. 클라이언트 상태는 표시용일 뿐이다.

```ts
export type PlaySession = {
  id: string;
  caseId: string;
  token: string; // httpOnly 쿠키 값 (추측 불가 32자)
  status: "IN_PROGRESS" | "COMPLETED";
  currentStepOrder: number; // 이 순서까지만 열 수 있다
  startedAt: string;
  lastSeenAt: string;
  completedAt?: string;
  completionCode?: string; // 79-1-XXXX
  redeemedAt?: string;
  isTest: boolean; // 테스트 모드 세션 → 통계 제외
};
```

### 잠금 판정 (순수 함수, 테스트 1순위)

```ts
type OpenResult =
  | { kind: "ALLOWED" } // step.order <= session.currentStepOrder
  | { kind: "NOT_STARTED" } // 세션 없음 → 시작 QR 안내
  | { kind: "LOCKED" } // step.order > currentStepOrder → 순서 안내
  | { kind: "COMPLETED" } // 이미 완료 → 인증 화면 재표시
  | { kind: "OTHER_CASE" }; // 다른 CASE의 QR을 찍음
```

URL을 직접 입력해도, UUID를 알아내도 잠금을 우회할 수 없다. 이것이 요구 11번의 답이다.
QR 토큰을 추측 불가한 10자로 두는 것은 보안이라기보다 **인쇄물 URL이 짧고 의도적으로
보이게** 하기 위함이다(현재 UUID 36자는 출력물에 어울리지 않는다).

## 5. 참가자 화면 — UX 설계

### 5.1 화면 목록과 강조점

| #   | 화면                        | 1순위 강조             | 카피(예)                                                                                                 |
| --- | --------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| 1   | 시작 표지 `/s/{entryToken}` | 사건 제목 + 단일 CTA   | `CASE 01 사라진 책의 행방` · `예상 15~20분` · `[사건 시작]` · `두 명이 한 대의 휴대폰으로 함께 진행해요` |
| 2   | 사건 소개 (INTRO)           | 배경 서사 가독성       | `책방지기는 경찰에 신고하지 않았습니다.` · `[사건 시작]`                                                 |
| 3   | 단서 찾기 (다음 QR 대기)    | 다음 행동 한 문장      | `두 번째 단서를 찾아주세요.` · 진행 점                                                                   |
| 4   | 문제 (QR 단계)              | 질문 + 입력 + 제출     | `01 / 04` · 힌트 배지 · `[정답 제출]`                                                                    |
| 5   | 오답                        | 재도전 유도(실패 아님) | `아직 사건의 핵심에 도달하지 못했어요. 문장을 다시 살펴보세요.`                                          |
| 6   | 정답 → 단서 공개            | 서사의 다음 조각       | `새로운 단서가 발견되었습니다.` + 연출 + `[다음 단서 찾기]`                                              |
| 7   | 순서 아님 (잠금)            | 현재 올바른 위치 안내  | `이 단서는 아직 차례가 아니에요. 지금은 두 번째 단서를 찾아야 해요.` · `[지금 단계로 돌아가기]`          |
| 8   | FINAL                       | 마지막 책 탐색         | `이제 마지막 책을 찾아주세요. 제목을 입력하면 사건이 종결됩니다.`                                        |
| 9   | CASE CLOSED                 | **완료 인증번호**      | `사건이 해결되었습니다` · `79-1-K7QP` · `직원에게 이 화면을 보여주세요`                                  |
| 10  | 재개·오류                   | 안심                   | `휴대폰을 바꿔도 이 링크를 다시 열면 이어서 할 수 있어요` / `연결이 불안정해요. 다시 시도`               |

### 5.2 강조의 계층 (모든 화면 공통)

1. **"지금 무엇을 해야 하는가" 한 문장** — 상단 고정. 이 한 문장이 없으면 화면이 실패다.
2. **행동 요소** — 입력창 또는 CTA 하나. 화면당 주요 버튼은 1개.
3. **완료 인증번호** — 완료 화면에서만 압도적으로 크게(직원이 1초에 확인).
4. **진행 상태** — 눈에 띄지 않게. 요구 10번의 "게임 UI처럼 만들지 말 것"을 지킨다.

### 5.3 하지 않을 것 (의도적 제외)

- 점수·랭킹·콘페티·카운트다운 타이머 (긴장 대신 압박, 그리고 서점의 조용한 분위기와 충돌)
- 회원가입·앱 설치·개인정보 수집 (요구 2·12번)
- 무한 스크롤형 긴 본문 (한 화면 한 메시지)
- 소리 자동 재생 — **효과음은 기본 꺼짐**. 켜는 배지를 노출하고 선택은 세션에 저장한다.

### 5.4 현장 현실 대응 (고객의 모자)

| 현실 문제                | 대응                                                                       |
| ------------------------ | -------------------------------------------------------------------------- |
| 15~20분 동안 화면이 꺼짐 | Wake Lock으로 진행 중 화면 유지 (미지원 브라우저는 무해하게 무시)          |
| 폰 배터리/브라우저 종료  | 같은 시작 QR을 다시 스캔하면 **진행 중 세션 이어가기** (새 세션 생성 금지) |
| 2인이 한 폰을 봄         | 본문 16px 이상, 질문 20px 이상, CTA 높이 48px 이상, 세로 1열               |
| 서점이 어두움            | 본문 대비 4.5:1 이상, 연출은 밝기 변화 최소                                |
| 카메라 앱으로 QR을 찍음  | 표준 URL만 사용(앱 스킴·커스텀 스킴 금지)                                  |
| 실수로 다른 QR을 찍음    | 잠금 화면에서 좌절시키지 않고 현재 위치를 알려줌                           |
| 네트워크 끊김            | 제출 실패 시 입력값 보존 + 재시도 버튼(입력을 다시 타이핑하게 만들지 않음) |
| 관리자 폰으로 설치 점검  | QR 점검 모드(티켓 14) — 각 카드 스캔 시 "QR 02 준비 완료" 즉시 판정        |

### 5.5 참가자 화면 구조 (라우트)

```
/s/$entryToken          시작(표지) + 세션 생성 또는 이어하기
/t/$qrToken             단계 진입(서버 잠금 판정 후 문제 또는 안내 화면)
/play/$caseId?step=N    세션 내부 이동(잠금된 단계만). QR 없이 이어보기용
```

기존 `/quest/$questId`는 `/t/$qrToken`으로 대체한다(실사용 데이터 없음).
`quest-qr-code.tsx`는 `entryToken`/`qrToken` 기반으로 교체한다.

## 6. 관리자 화면 — UX 설계

데스크톱 우선. 정보 밀도 높은 목록 + 우측 편집 패널. 파괴적 동작은 outline 버튼 + 확인 다이얼로그.

| 화면                                 | 핵심                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------- |
| `/admin` 대시보드                    | 진행 중 CASE, 전체 CASE, 오늘 참가/완료, [새 CASE 만들기]               |
| `/admin/cases`                       | CASE 카드: 상태 배지 · 단계 수 · [편집] [미리보기] [통계] [복제] [삭제] |
| `/admin/cases/$caseId`               | STEP 목록(드래그 순서 변경) + 상태 전환 + [QR 출력]                     |
| `/admin/cases/$caseId/steps/$stepId` | STEP 편집기(기본정보 → 콘텐츠 → 질문/정답 → 피드백 → 연출) + 미리보기   |
| `/admin/cases/$caseId/preview`       | PC/모바일 프레임, **저장 전 초안 반영**, [테스트로 열기]                |
| `/admin/redeem`                      | 직원용 4자리 코드 입력 → 즉시 판정                                      |
| `/admin/cases/$caseId/stats`         | 완료율 · 평균 시간 · 단계별 도달/이탈/정답률 · 힌트 사용                |

관리자 화면에서 반드시 지킬 3가지:

1. **미리보기 버튼이 항상 화면 안에 있다.** 저장하지 않은 초안 상태로 미리보기 → 확인 후 저장.
   (`이 화면을 보면 참가자에게 어떻게 보이는지 바로 알 수 있다`가 CMS의 존재 이유다)
2. **LIVE 전환 시 검증하고, 막는다.** QR 단계에 정답·정답 유형이 없거나 순서에 구멍이 있으면
   위반 목록을 보여주고 LIVE를 거부한다. 현장에서 발견하는 것보다 여기서 막는 게 싸다.
3. **CASE 복제가 1클릭.** CASE 01 → CASE 02의 기본 구조. 새 케이스 제작의 90%가 복제로 시작한다.

## 7. QR 운영 원칙 (요구 23번 = 되돌릴 수 없는 실수 방지)

- QR은 **고정 URL**만 담는다: `/s/{entryToken}`, `/t/{qrToken}`. 콘텐츠는 서버에서 조회.
  질문·정답·이미지를 아무리 고쳐도 **출력한 QR을 다시 붙이지 않는다.** → 회귀 테스트로 고정한다.
- 출력물: 단계별 PNG/SVG 개별 다운로드 + 전체 인쇄용 시트(단계 번호·제목·QR·짧은 안내).
  인쇄물에 **단계 번호를 크게** 넣는다 — 잘못 붙였을 때 즉시 눈에 띄게.
- 토큰 재발급은 제공하되 "기존 인쇄물이 모두 무효가 된다"고 명시적으로 경고한다.
- 설치 당일 점검 모드로 카드 전량 스캔 → 순서 오류 0으로 시작.

## 8. 미디어·연출 (카톡 아이디어의 현실적인 구현)

논의된 아이디어 중 비용 대비 효과가 높은 것만 채택한다.

| 아이디어                           | 결정                                                                                    | 이유                                                               |
| ---------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 두루마리 펴짐 / TV 텍스트 / 타자기 | **채택 — CSS 연출 프리셋 5종** (`UNROLL`, `FADE_UP`, `TYPEWRITER`, `TV_SCAN`, `GLITCH`) | 영상 업로드 없이 즉시 사용, 선명, 용량 0, 관리자는 드롭다운만      |
| 게임 효과음(uisfx 등)              | **부분 채택 — 내장 효과음 2~3개, 기본 꺼짐**                                            | 라이선스 안전 + 서점의 조용한 환경 배려                            |
| 동영상(MP4)                        | **채택 — 단계 미디어로 mp4, 용량 상한 + 자동 압축/포스터**                              | 요구된 "이야기를 만들어서" 영상 삽입                               |
| 이미지 업로드 실패 문제            | **즉시 수정** — 실제 한도·파일 크기 표시 + 자동 압축                                    | 9/5 실제 클레임                                                    |
| 이모지                             | 채택(콘텐츠 텍스트에 그대로 사용 가능, 추가 작업 없음)                                  | —                                                                  |
| 음성 합성(TTS, fish.audio)         | **보류**                                                                                | 외부 API·비용·한국어 품질 편차. 연출 프리셋과 효과음으로 먼저 검증 |
| 커스텀 사운드 업로드 / Lottie      | 보류                                                                                    | 필요해지면 그때                                                    |

**연출의 철학**: 연출은 장식이므로 정보를 지체시키면 안 된다.
`prefers-reduced-motion`이면 연출을 생략하고 텍스트를 **즉시** 표시한다(내용 손실 0).
텍스트는 연출 시작 후 1초 이내에 읽을 수 있어야 한다.

**불변식(회귀 테스트로 고정)**

1. 참가자용 API 응답에는 `answer`/정답 정보가 절대 포함되지 않는다.
2. 순서를 건너뛴 단계는 서버가 거부한다(잠금은 클라이언트에 의존하지 않는다).
3. 스텝 내용을 수정해도 `qrToken`/`entryToken`은 변하지 않는다(QR 재출력 불필요).
4. 같은 시작 QR 재스캔은 진행 중 세션을 이어가며 새 세션을 만들지 않는다.
5. 테스트 모드 세션은 통계에 포함되지 않는다.
6. 업로드 실패 시 사용자에게 **실제 한도와 실제 파일 크기**가 숫자로 보인다.

## 10. 로드맵

### Phase 0 — 운영 준비 (0.5~1일) · 티켓 10

업로드 실패 안내 + 용량 자동 압축 + 그룹 삭제. 사장님이 이미 겪은 문제를 먼저 없앤다.
배포(티켓 09)는 계정 작업이라 사람 손이 필요하므로 별도로 계속 진행한다.

### Phase 1 — 투어가 실제로 돈다 (약 1주) · 티켓 11 → 12

CASE/STEP/SESSION 모델과 마이그레이션, 참가자 전 구간(시작 → 소개 → QR×4 → FINAL → CLOSED),
서버측 잠금, 재개. **여기까지 되면 체험비를 받고 실제로 운영할 수 있다.**
이 시점의 콘텐츠는 admin UI가 아니라 DB 시드로 넣어도 된다.

### Phase 2 — 사장님이 혼자 운영한다 (약 1주) · 티켓 13 → 14

CASE/STEP 편집기, 복제, 상태 전환 검증, 미리보기, 테스트 모드,
QR 출력 시트와 설치 점검 모드. **여기까지 되면 개발자 없이 CASE 02를 만들 수 있다.**

### Phase 3 — 경험과 운영 데이터 (1~2일) · 티켓 15, 16

연출 프리셋·효과음·동영상, 완료 인증번호와 리딤 화면, 통계.
연출은 Phase 1 직후에 넣어도 되지만, 운영 자체가 먼저다.

### Build order

```
10 (핫픽스) → 11 (모델) → 12 (참가자 플로우) → 16a (완료 인증번호)
→ 13 (관리자 편집기) → 14 (QR 운영) → 15 (연출/미디어) → 16b (통계)
```

11은 12·13·14의 공통 선행 조건이므로 쪼개지 않는다.
